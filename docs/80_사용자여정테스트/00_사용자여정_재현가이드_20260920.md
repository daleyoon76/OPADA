# OPADA 사용자 여정 재현 가이드

> 원본 방법론: `helix-10/docs/samnyeon-user-journey-playbook.md`(삼년 프로젝트). §0 원칙만 가져오고 내용은 OPADA 화면 기준으로 새로 작성했다.
> 이 문서는 "어떻게 테스트할지"만 담는다. "무엇을 발견했는지"는 매 회차 `docs/80_사용자여정테스트/results/YYYY-MM-DD-journey-결과.md`에 따로 남긴다.

## 0. 원칙

1. **실제 버튼·링크 클릭으로만 이동한다.** `location.hash`를 직접 바꾸는 우회 이동은 새 탭을 열 때처럼 불가피할 때만 쓰고, 그때는 "직접 이동"이라고 기록한다.
2. **"에러가 안 떴다"로 확인을 끝내지 않는다.** 화면에 나온 문구·숫자·배지가 실제로 입력한 값이나 실제 온비드 원문과 맞는지 대조한다.
3. **의심스러운 화면은 `src/app.js`나 `src/server.py`의 관련 코드를 읽고 근거를 확인한 뒤에만 버그 또는 정상이라고 판정한다.** 추측만으로 판정하지 않는다.
4. **사용자 유형 4종(개인사업자·개인·법인·예비창업자)과 검토 목적 3종(임대/대부·매각/공매·창업 공간)은 화면 동작이 실제로 달라지는 조합만 추려서 누른다.** 코드 기준(§2-1)으로 이미 추려 뒀으므로 매 회차 새로 추릴 필요는 없다.
5. **온비드 URL은 수명이 짧다.** §3의 URL은 이 문서를 쓴 시점(2026-09-20) 기준이며, 다음 회차에는 먼저 열어서 유효한지 확인한다.

## 1. 사전 준비

- 서버가 살아있는지: `curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:8975/` → `200`.
  죽어 있으면 `ps aux | grep server.py`로 PID 확인 후 `cd src && python3 server.py &`.
- 코드를 고쳤다면 서버를 재시작해야 반영된다(정적 파일은 `translate_path`가 요청마다 디스크를 읽어 재시작 없이 반영되지만, `server.py` 자체의 로직 변경은 프로세스 재시작이 필요하다).
- 시연용 URL은 `docs/60_본선준비/03_시연용_실URL_20260902.md`에 있다. 마감이 지났을 수 있으니 먼저 열어서 확인한다.
- 이 프로젝트는 로그인·회원가입이 없다. 삼년 플레이북의 "계정 이메일 규칙"·"학생/학부모 역할 분리" 절은 대응 개념이 없어 옮기지 않았다.

## 2. 화면별 재현 절차

### 2-1. 사용자 유형 × 검토 목적 — 실제로 동작이 달라지는 조합

`src/app.js`를 근거로 조합을 추렸다(§2-1은 코드 재확인 없이는 고치지 않는다).

- **사용자 유형**은 `boardTasks`의 `userTypes` 필드(`src/app.js:224` 부근)와 `DOC_GROUP_CONDITION_USER_TYPES`(`src/app.js:990`)에 배선돼 있다.
  - `개인사업자(sole)` — 준비 보드에 "사업자등록증명 준비처" 항목만 단독으로 뜬다.
  - `개인(person)`·`예비창업자(founder)` — "신분 확인 서류 준비처" 항목이 뜨고, 서류 조건 아코디언의 `person` 그룹(개인·개인사업자·예비창업자 공통)이 자동으로 펼쳐진다. **두 유형은 배선상 동일하게 동작한다** — 실측에서 다른 점이 나오면 그 자체가 결함이다.
  - `법인(corp)` — "법인 증빙서류 준비처" 항목이 뜨고, 아코디언의 `corp` 그룹만 자동으로 펼쳐진다.
- **검토 목적**은 `getFitMessage()`(`src/app.js:785` 부근)에 배선돼 있다.
  - `매각/공매 공고 검토(sale)` — 분석된 공고가 매각·공매·압류 계열이 아니면 "목적과 입력 공고 유형이 다릅니다"(불일치) 배지가 뜬다.
  - `임대/대부 공고 검토(lease)` — 분석된 공고가 매각 계열인데 임대가 아니면 불일치 배지가 뜬다.
  - `창업 공간 탐색(startup)` — 공고 유형과 무관하게 항상 "확인 필요" 배지가 뜬다.

실제로 눌러 볼 조합 4가지(유형 3종 각 1회 + founder=person 배선 확인용 1회):

| # | 사용자 유형 | 검토 목적 | 공고 유형 | 기대 배지 |
|---|---|---|---|---|
| 1 | 개인사업자 | 매각/공매 검토 | 매각 공고 | 일치(사업자등록증명 항목) |
| 2 | 개인 | 임대/대부 검토 | 임대 공고 | 일치(신분 확인 서류 항목) |
| 3 | 법인 | 창업 공간 탐색 | 아무 공고 | 확인 필요(법인 증빙서류 항목) |
| 4 | 예비창업자 | 매각/공매 검토 | 임대 공고 | 불일치(개인 항목 — #2와 아코디언·보드 항목 동일해야 함) |

### 2-4. 서류 체크리스트 아코디언 (법인·개인 조건 실공고 검증)

2026-09-18 신설(`790a303`) 기능. 지난 회차 보고서에 이 검증이 빠져 있었다고 명시적으로 남아 있어, 이번 회차는 실공고 기준으로 반드시 채운다.

- 조건 그룹은 `<details class="doc-group">`로 감싸여 있고, `getDocGroupUserTypes()`가 그룹 안 서류의 `conditionKeys`(`corp` 또는 `person`)를 보고 현재 선택된 사용자 유형과 일치하면 `open` 속성을 붙여 기본으로 펼친다.
- 확인 절차:
  1. 법인·개인 조건이 실제로 함께 있는 공고(§3-3)를 분석한다.
  2. 사용자 유형을 `법인`으로 바꾼 뒤, `법인 조건` 그룹만 펼쳐져 있고 `개인` 계열 그룹은 접혀 있는지 확인한다.
  3. 사용자 유형을 `개인`으로 바꾼 뒤, 반대로 펼쳐지는지 확인한다.
  4. 그룹 안 각 서류 항목의 "원문 근거" `<details>`를 펼쳐 실제 온비드 원문 문장과 대조한다.
  5. `개인사업자`·`예비창업자`로도 바꿔서 `개인` 그룹과 같게 펼쳐지는지 확인한다(§2-1의 배선 동일성 재확인).

### 2-5. 온비드 공고상세 URL 직접 입력

과거 500 에러가 있었던 경로다(`known-pitfalls.md` "온비드 URL" 절). 온비드 쪽 문제인지 우리 쪽 문제인지 구분해서 기록한다.

- **공고상세(`mvmnPbancDtl.do`) URL**을 그대로 `#input`에 붙여넣어 분석한다(표본 23건이 전부 이 형식).
- 분석 결과에서 만들어지는 "물건상세(`itemDetail`)" 링크를 실제로 클릭해 새 탭으로 연다.
- `pbctCdtnNo`가 없는 공고상세 입력에서는 `itemDetailUncertain: true`가 붙고 실제로 HTTP 500이 나는 것이 **알려진 정상 동작**이다(온비드 쪽 제약 — 우리 쪽 결함이 아니다). 화면에 "(열리지 않을 수 있음)" 안내가 실제로 붙어 있는지가 확인 포인트다.
- 물건상세(`mvmnCltrDtl.do`) URL을 직접 입력하는 경로도 1건 함께 확인해 대조한다 — 이 경로는 `pbctCdtnNo`를 이미 갖고 있어 물건상세 링크가 정상 열려야 한다.

### 2-7. 반응형 (390px)

- 브라우저 창 폭을 390px로 줄인다(모바일 폭).
- `#input`·`#report`·`#watchlist` 세 화면을 순서대로 열어 지원 패널(하단 접힘 패널 7종, 서류 아코디언, 처리 단계)이 겹치거나 잘리지 않는지 확인한다.
- `field-row`(사용자 유형·검토 목적 select 2개)가 좁은 폭에서 어떻게 줄바꿈되는지 확인한다.

### 2-8. 인쇄용 화면

- `src/styles.css`에 `.print-sheet`·`#view-print`·`@media print` 규칙이 있다(§7 원칙에 따라 코드 확인 후 판정).
- **코드 확인 결과**: `src/index.html`·`src/app.js` 전체에 `view-print`·`print-sheet`를 참조하는 곳이 없다. 이 CSS를 실제로 트리거하는 버튼이나 JS 함수가 없다. `git log -S"view-print"`로 확인하면 최초 커밋(`992664b`)부터 지금까지 이 상태 그대로다.
- 따라서 이 항목은 "실제 렌더링을 확인"할 대상이 화면에 없다. 브라우저 인쇄(Cmd+P)를 눌러도 이 CSS가 적용될 경로가 없으므로, 매 회차 다시 찾아보지 말고 이 문서의 기록으로 대체한다. 최종 결정(기능을 만들지, CSS를 정리할지)은 결과 문서에 제안으로만 남긴다.
