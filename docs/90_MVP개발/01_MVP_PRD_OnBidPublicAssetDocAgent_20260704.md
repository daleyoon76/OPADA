## 1. 목표

KAMCO 심사위원이 `이 팀이 선정되면 실제로 이런 형상의 서비스가 나오겠다`고 이해할 수 있도록, 온비드 공개 공고 1건을 기준으로 공고 가져오기부터 준비 보드, 서류 준비처 링크, 담당기관 확인 질문, 관심 공고 관리까지의 핵심 흐름을 작동하는 화면으로 보여준다.

이 MVP는 운영 서비스가 아니라 제출 증빙용 프로토타입이다. 온비드 공개 페이지와 short URL을 서버에서 읽고, 공공데이터포털 인증키가 있으면 온비드 공공데이터 API로 물건/입찰 정보를 보강한다.

## 5. 분석 데이터

기본 샘플은 온비드 공개 공고 페이지에서 확인 가능한 공고를 사용한다. 사용자가 다른 온비드 공고/물건 URL을 입력하면 로컬 분석 API가 해당 페이지를 가져와 같은 스키마로 변환한다.

| 항목 | 내용 |
| --- | --- |
| 공고 | 202605-13728-00, 2026년도010회 국유재산 대부입찰 공고 |
| 공고기관 | 한국자산관리공사 |
| 재산유형 | 국유재산 / 임대 |
| 입찰방식 | 일반경쟁(최고가방식) / 총액 |
| 입찰구분 | 전자입찰 |
| 출처 | 온비드 공고 상세 공개 페이지 |

MVP는 기본 샘플 공고를 포함하되, 로컬 분석 API가 온비드 공고/물건 URL을 서버에서 가져와 주요 표시값을 표준 입력 스키마로 추출한다. short URL은 최종 온비드 URL로 따라간 뒤 분석한다. 공공데이터포털 인증키가 있으면 `OnbidRlstDtlSrvc2`, `OnbidCltrBidDtlSrvc2`, `OnbidPbancDtlnfSrvc2`, `OnbidPbancBidDtlSrvc2`를 호출해 물건상세와 입찰정보를 보강한다. 화면에는 `실제 온비드 페이지 분석`, `API 연결/키 없음`, `원문 확인 필요`, `법률/투자 판단 아님`을 명시한다.

## 6. 사용자 흐름

1. 사용자가 온비드 공고 URL 또는 공고번호를 입력한다. URL이 있으면 공고번호와 물건번호는 시스템이 자동 추출한다.
2. 사용자는 본인 유형과 내 검토 목적만 선택한다.
3. `공고 분석`을 누르면 시스템은 공고 유형과 사용자 목적이 맞는지 먼저 판정한다.
4. 사용자는 준비 보드에서 핵심 요약, 오늘 할 일, 마감 알림 후보, 비용 후보를 확인한다.
5. 사용자는 각 할 일을 펼쳐 준비처 링크, 담당기관 질문, 원문 근거를 확인하고 완료 상태를 체크한다.
6. 사용자는 관심 공고 보드에서 여러 공고의 마감과 준비상태를 비교한다.
7. 필요하면 준비 보드의 핵심 내용을 검토 메모로 복사해 담당기관 문의나 공동 검토에 활용한다.

## 8. 인수 조건

- 로컬 서버에서 `index.html`이 열리고 주요 화면이 정상 표시된다.
- URL 입력/사용자 유형 선택/분석 버튼이 동작한다.
- 온비드 공고/물건 URL 또는 short URL을 입력하면 서버가 최종 페이지를 가져와 주요 필드를 추출한다.
- 샘플 공고의 주요 필드가 준비 보드에 표시된다.
- 준비 보드 화면에 오늘 할 일, 공식 준비처 링크, 담당기관 질문, 원문 근거, 마감/비용 후보가 모두 표시된다.
- 관심 공고 화면에 여러 공고의 준비상태와 다음 확인 항목이 표시된다.
- 모든 화면에 `법률/투자 판단 아님`, `원문 확인 필요` 취지의 고지가 포함된다.
- Playwright 또는 브라우저 캡처로 3~5장 스크린샷을 저장할 수 있다.

## 9. 신청서 반영 문장 후보

> 제출 준비 과정에서 공개 온비드 공고와 물건 URL을 입력해, 공고 가져오기, 공고 유형 판정, 체크 가능한 준비 보드, 서류 준비처 링크, 담당기관 확인 질문, 관심 공고 관리까지의 핵심 MVP 화면을 구성하였다. 현재 로컬 MVP는 온비드 short URL을 최종 상세 URL로 따라가 주요 필드를 추출하며, 공공데이터포털 인증키가 있으면 온비드 물건상세/입찰정보 API로 값을 보강하는 구조까지 구현했다.

> 본 서비스는 낙찰 가능성이나 투자수익률을 판단하지 않는다. 공고 원문과 공공데이터를 사용자가 실행 가능한 준비 보드로 바꾸고, 서류 준비처와 담당기관에 확인해야 할 질문을 정리하는 공공데이터 기반 준비 보조 Agent다.
