# LLM 질문-답변 기능 원가 분석과 요금제 제안

- 작성: 2026-09-21 (lunch-loop 자율 작업 창, 11:10~14:00 KST)
- 대상 기능: 준비 보드 "궁금한 점을 물어보세요" — `POST /api/ask`(`src/server.py:2350`), 처리 함수 `answer_notice_question()`(`src/server.py:1797`)이 `vertex_answer_question()`(`src/server.py:1735`) → `gemini_answer_question()`(`src/server.py:1770`) 순으로 폴백
- 모델: `gemini-2.5-flash-lite`(코드 상수, `src/server.py:1774` 기본값)
- 구현·요금제 확정은 하지 않았다. 이 문서는 원가 계산과 제안까지다.

## 1. 요청 1건의 구조

`question_prompt()`(`src/server.py:1701`)가 만드는 JSON을 그대로 모델에 보낸다. 필드는 고정 instruction 문장 + notice 10개 필드 + `requiredDocs` 최대 10개 + 사용자 질문(최대 500자, `src/server.py:2355`에서 자름) + 고정 schema다.

실제 함수를 호출해 현실적인 표본(공고 필드 10개·서류 10개·질문 45자)으로 페이로드 문자 수를 실측했다.

- 전체 프롬프트 JSON 문자 수: **993자**
- 그중 고정 instruction 문장: 325자
- 질문이 상한(500자)까지 차면 프롬프트 총 길이는 약 **1,450자**까지 늘어난다

출력은 `generationConfig.maxOutputTokens: 400`으로 상한이 걸려 있다(`src/server.py:1753`, `1780`). 실제 응답은 `{"answerable": bool, "answer": "...", "sourceField": "..."}` 뿐이고, instruction이 "한국어 1~2문장으로 짧게"를 명시하므로 상한을 다 쓰는 경우는 드물 것으로 예상한다(관측치 아님 — 실호출 미검증 항목, 아래 §4).

## 2. 토큰 수 추정 방법과 한계

이 기기에 `GEMINI_API_KEY`/`GOOGLE_API_KEY`도 gcloud Vertex 인증 토큰도 없어(known-pitfalls.md 기존 기재와 동일 확인, 2026-09-21 재확인) Vertex AI의 공식 `count_tokens` API를 호출해 정확한 토큰 수를 잴 수 없었다. **아래 수치는 추정치이고 [추론]이다.**

- 업계에서 통용되는 근사치는 "영어 텍스트 1토큰 ≈ 4자"이지만, 한국어처럼 조사·어미가 붙는 언어는 토큰 밀도가 더 높다(1토큰당 문자 수가 더 적다)는 것이 일반적으로 알려진 경향이다.
- JSON 구조 문자(따옴표·콜론·중괄호·영문 키)는 ASCII라 토큰 밀도가 낮다(1토큰당 문자 수가 더 많다).
- 두 성질을 섞어 프롬프트 전체(993자, 한국어 본문 약 70% + JSON 구조/영문 약 30%)를 **약 600~750 토큰**으로 추정한다. 질문이 상한까지 찰 때(약 1,450자)는 **약 850~1,050 토큰**으로 추정한다.
- 출력은 상한 400토큰이지만, "1~2문장" 지시와 스키마 크기를 볼 때 전형적인 응답은 **약 60~150 토큰**으로 추정한다. 모델이 상한을 다 쓰는 최악의 경우도 계산에 함께 넣는다.

## 5. "무료 3회 / 유료 20회" 아이디어 검증

- 무료 사용자 1명이 3회 질문: 원가 약 0.45~1.1원
- 유료 사용자 1명이 20회 질문: 원가 약 3~7.3원

둘 다 **원가만 놓고 보면 무시할 수 있는 금액**이다. 이 기능의 API 호출 원가는 한도를 촘촘하게 설계해야 할 만큼 크지 않다. 즉 "무료 3회/유료 20회"라는 숫자는 원가로 정당화되지도, 반박되지도 않는다 — 원가는 이 결정에 실질적인 제약을 주지 않는다.

마진율 가정은 계산하지 않았다. 이 기능은 아직 유료 요금제 가격 자체가 정해지지 않은 MVP 단계라 "가격 대비 원가 비율"을 계산할 분모가 없다. 다만 원가가 요청당 1원 미만이므로, 어떤 합리적인 유료 가격을 매기더라도 이 기능 하나의 API 원가가 마진을 깎아 먹을 걱정은 사실상 없다고 말할 수 있다.

## 6. 원가 기반 제안

- **한도를 두는 이유는 원가 방어가 아니라 다른 것이어야 한다.** 후보는 ⑴ 악용 방지(자동화된 대량 질문으로 응답 품질 저하나 서비스 신뢰 문제), ⑵ Vertex AI/Gemini API 쪽의 요청 빈도 제한(원가와 무관한 분당 요청수·분당 토큰수 쿼터 — 이번 조사 범위 밖, 미확인), ⑶ 제품 포지셔닝(무료/유료 구분을 명확히 보여주는 장치)이다.
- 원가만 근거로 삼는다면 "무료 3회/유료 20회"보다 **훨씬 후한 한도**(예: 무료 10~20회/일, 유료는 사실상 무제한에 가까운 수준)도 감당할 수 있다. 원가 상한선은 무료 사용자 1,000명이 하루 20회씩 써도 약 3,000원 수준이다(0.15원 × 20 × 1,000).
- 반대로 "무료 3회/유료 20회"를 그대로 채택해도 원가 문제는 없다 — 다만 그 숫자의 근거를 원가가 아니라 ⑴~⑶에서 다시 찾아야 한다.
- **제안:** 원가는 한도를 정하는 제약 조건이 아니므로, 실제 한도는 ⑴ 악용 방지에 필요한 최소한의 수준과 ⑵ 유료 전환을 유도하고 싶은 정도(제품·마케팅 판단)로 정하기를 권한다. 원가 근거로 굳이 좁힐 필요가 없다는 것이 이 조사의 핵심 결론이다.

## 7. 검증 경계

- 구현됨: 없음(이 문서는 분석·제안만, 코드 미수정)
- 로컬 검증됨: `question_prompt()` 실제 호출로 페이로드 문자 수 실측(§1)
- 미검증: 실제 Vertex AI/Gemini API 호출로 잰 정확한 토큰 수 — 이 기기에 인증 수단이 없어 `count_tokens` API를 부르지 못했다. 위 토큰 추정치(§2)는 문자 수 기반 근사이며 실측이 아니다
- 미검증: Vertex AI 쪽 공식 가격 페이지 1차 확인 — 콘텐츠 길이로 페치 실패, 2차 소스 교차 확인으로 대체
- 다음 검증 후보: 인증키 확보 시 `count_tokens` API로 실측 토큰 수 확인 → 이 문서의 추정치를 관측치로 교체

## 8. 결정 요청

요금제 확정은 사용자 승인 사안이다. 아래 중 결정이 필요하다.

- 무료/유료 한도를 원가가 아닌 다른 기준(악용 방지·제품 포지셔닝)으로 다시 정할지, 아니면 "무료 3회/유료 20회"를 그대로 채택할지
- 채택한다면 구현 착수 여부와 시점
- 모델 은퇴 예정일(2026-10-20 전후)과 결선 일정이 겹치는지 별도로 확인할지
