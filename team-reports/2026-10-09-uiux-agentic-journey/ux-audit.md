# OPADA 준비 보드 — 단계형 플로우 + 질문-답변 온보딩 UX 설계 검토

> 반환자: ux-flow-auditor (3팀 UIUX품질팀). 읽기 전용 진단. 코드 변경 없음.
> 읽은 파일: `src/app.js`, `src/server.py`, `src/index.html`, `handoff.md`, `docs/60_본선준비/19_AI가이드형_UX_재설계_플로우_20261001.md`

## 조사 범위와 확인한 사실 [관측]

- `src/server.py` `build_tasks()`(1309행)가 만드는 할 일은 **5개 고정 id**: `notice-type`·`bid-period`·`price`·`documents`·`agency`.
- `src/app.js` 1~400행대의 하드코딩 `sampleNotice.boardTasks`(`guarantee`·`business-cert`·`identity-cert`·`corp-cert`·`joint-bid`·`agency-question`)는 **다른 id 체계**입니다.
  - `load-sample` 핸들러(1885행)가 이 객체를 불러오지만 `analyzedInputValue = ""`로 두므로 `isAnalyzedInputCurrent()`가 거짓이 되어 `getFitMessage()`가 즉시 "아직 분석하지 않았습니다" 차단 화면을 띄웁니다(1412행 `staleInputWarning`).
  - 즉 이 6개 id 세트는 실제로 화면에 렌더되지 않는 **죽은 데이터**입니다[관측]. 이번 단계 설계는 서버가 만드는 5개 id 세트를 기준으로 합니다.
- `getApplicableTasks()`(755행)는 할 일을 **AI 매칭 점수 내림차순**으로 정렬합니다. 단계 그룹과 무관한 정렬 키라서 단계화 작업과 바로 충돌할 지점입니다.
- `documents` 태스크의 상세 문구(`server.py` 1358행)는 이미 "이 목록은 참고용이며 빠진 항목이 있어도 진행을 막지 않습니다"라고 명시합니다. 서류 체크리스트(`doc-checklist`)를 완료 게이트에 넣으면 이 기존 카피와 정면으로 모순됩니다.
- 상단 고지 밴드(`index.html` 32행)는 "원문과 담당기관 확인을 우선합니다"를 전역 약속으로 걸어 둡니다.
- `index.html`에 이미 `currentStage`·`pipelineSteps`라는 이름이 **Step1 분석 파이프라인**(`#pipeline`, 85행)에 쓰이고 있습니다(`app.js` 1895·1903행). 이번에 만들 "단계" 개념과 이름이 겹치면 혼선·버그 위험입니다.
- 질문-답변 기능(`/api/ask`, `renderBoardCoach` 993행)과 용어 사전(`glossary-list`, 1346행)이 이미 구현돼 있습니다. 온보딩 설계는 이 둘을 재사용하는 방향으로 짰습니다.
- `tests/test_screen_strings.py` 금지 문구 14종 중 "Q&A"가 포함돼 있어, 질문-답변 UI의 화면 문구에 "Q&A"라는 표기를 쓰면 안 됩니다.

## ⑴ 상태 모델

### 단계 구성

| 단계 | 포함 task id | 비고 |
|---|---|---|
| 1단계 · 공고 확인 | `notice-type`, `bid-period` | 분석 직후 값이 이미 채워져 있어 확인 위주 — 마찰 가장 적은 단계 |
| 2단계 · 서류 준비 | `documents` (+ `doc-checklist` 참고용) | 체크리스트는 게이트에 넣지 않음(아래 근거) |
| 3단계 · 입찰 참여 | `price`, `agency` | 제안된 구성 그대로 |

### 완료·열림 조건

- **단계 완료**: 그 단계에 속한 모든 task id의 `getTaskState()[id] === true`.
- **다음 단계 열림**: 이전 단계가 완료되면 열림. **별도의 "unlock" 플래그를 localStorage에 저장하지 않고, 매 렌더마다 체크 상태에서 파생 계산**합니다.
  - 이유: 잠금 여부를 별도 상태로 저장하면 체크 상태와 잠금 상태 두 소스가 갈릴 수 있습니다(전역 지침 P-40 "계약을 한 곳으로 확정" 원칙과 같은 위험군). 체크박스가 유일한 진실의 소스여야 합니다.
- **되돌리기 처리**: `getTaskState()`가 localStorage 기반이라 1단계 체크를 해제할 수 있습니다. 이 경우 **다음 단계는 즉시 재잠김** — 단, 2·3단계에 이미 체크해 둔 값은 지우지 않습니다. 다시 1단계를 완료하면 이전 체크 상태 그대로 복원됩니다. (데이터는 보존하고 접근만 다시 막는 방식.)

### 서류 체크리스트와 2단계 완료의 관계

- **`documents` task 체크 하나로 2단계 완료 조건을 충분히 봅니다.** `doc-checklist` 전체 완료는 게이트에 넣지 않습니다.
- 근거: `documents` task의 기존 상세 문구가 "참고용이며 빠진 항목이 있어도 진행을 막지 않습니다"라고 이미 약속하고 있습니다. 체크리스트를 게이트로 쓰면 이 문구를 거짓으로 만듭니다.
- 또한 체크리스트는 공고마다 그룹이 비거나(`groupsHtml` fallback), 사용자 유형별로 관련 없는 항목이 접혀 있는 구조라 "전체 완료"라는 개념 자체가 모든 공고에서 성립하지 않습니다.
- 대신 체크리스트가 안 끝난 채 3단계로 넘어가면, 2단계 요약 배지에 "서류 체크리스트 N/M 남음" 같은 **비차단 리마인더**만 남깁니다.

### 잠긴 단계의 표시

- **완전히 숨기지 않습니다.** 1단계 진입 시점부터 3단계까지 제목·아이콘이 모두 보여야 합니다.
- 잠긴 단계 카드는 **미리보기 상태**로 보입니다: 단계명, 포함 task 제목, "1단계를 마치면 열립니다" 한 줄.
- 체크박스는 **비활성화**하되, 다음은 잠금과 무관하게 **항상 클릭 가능**해야 합니다.
  - "온비드 원문" 링크, "담당기관에 물어볼 질문" 문구, "자세히" 상세 설명, 공고 원문에서 확인된 값.
  - 이유: 상단 고지("원문과 담당기관 확인을 우선합니다")가 전역 약속이라, 어떤 화면 상태에서도 정보 열람 자체를 막으면 그 약속을 어깁니다. 체크=완료 표시만 잠그고, 정보 열람은 절대 잠그지 않습니다.

### 구현 시 반드시 지킬 것 (표시/진실 소스 분리)

- `getApplicableTasks()`의 aiMatch 점수 정렬은 **단계 경계를 넘어 재배치하면 안 됩니다.** 단계가 1차 정렬 키, 점수는 같은 단계 안에서만 2차 기준.
- `getTaskSummary().nextTask`는 "전체 점수 정렬 중 첫 미완료"가 아니라 "가장 앞선 미완료 단계의 첫 미완료 task"로 재정의해야 합니다. 관심 공고 탭의 `currentNoticeCard().next`가 이 값을 그대로 쓰고 있어, 재정의하지 않으면 거기서도 단계 순서가 깨집니다.
- 변수명 `currentStage`는 기존 분석 파이프라인(Step1)이 이미 쓰고 있습니다. 새 단계 상태는 다른 이름(예: `prepStage`)을 씁니다.

## ⑵ 질문-답변 온보딩 플로우

### 시점과 범위

- **분석 성공 직후, 준비 보드 최초 진입 시 1회**. 매 공고 분석마다 다시 묻지 않습니다 — 경험 수준은 공고가 아니라 사용자 속성이기 때문입니다.
- 저장은 **노티스 무관 전역 localStorage 키**(기존 `taskStorageKeyFor(notice)` 패턴과 분리). 다른 공고를 분석해도 유지됩니다.
- 답을 나중에 바꿀 수 있는 작은 토글을 상시 노출합니다(예: 진행률 영역 옆 "안내 수준: 자세히 ⇄ 간단히"). 자가 진단이 틀렸을 때 되돌릴 길이 있어야 합니다.

### 질문 구성 — 2개, 역할이 다름

**질문 A (선택지형, 필수 노출·스킵 가능)**

> "온비드 공매·입찰, 해 보신 적 있으신가요?"
> - [처음이에요] / [몇 번 해봤어요] / (건너뛰기)

- 스킵 시 기본값은 **"처음이에요" 쪽**(더 많이 설명하는 쪽)으로 둡니다. 과설명의 비용보다 초보자가 덜 설명받아 놓치는 비용이 더 큽니다.
- 효과(표시 로직만, 판단 로직 변경 없음):
  - "처음이에요" → 각 task의 "자세히" `<details>` 기본 `open`, 용어 사전 탭(`glossary-list`) 배지를 눈에 띄게, 온보딩 자체 안내문을 조금 더 길게.
  - "몇 번 해봤어요" → "자세히" 기본 닫힘, 제목·배지 중심의 축약 표시, 용어 사전은 탭에 있지만 강조 없음.

**질문 B (자연어, 완전 선택)**

> "지금 궁금한 점이 있으면 먼저 물어보세요."

- 새 판정 로직을 만들지 않습니다. **기존 `/api/ask`·`renderBoardCoach`의 질문 입력창을 분석 직후 화면 맨 위로 끌어올려 먼저 노출**하는 것으로 충분합니다.
- "AI가 판단하지 않는다" 원칙과 헤지 표현은 기존 `getAiPrecheckForTask`·질문-답변 경로 그대로 유지됩니다.
- 질문 B는 완전히 스킵 가능하고, 답하지 않아도 화면 흐름을 막지 않습니다.

### 질문 A 2개로 줄인 이유 [추론]

"경험 수준"과 "지금 알아보는 단계인지 입찰까지 생각 중인지"를 각각 묻는 3문항 안도 검토했으나, 기각했습니다. 뒤 질문은 기존 `aiMatch`가 이미 자동으로 하는 일과 겹치고, 질문을 늘릴수록 분석 직후 첫 화면의 마찰이 커집니다.

## ⑶ 기존 select와의 관계

| | `user-type`(사용자 유형) | `asset-focus`(검토 목적) | 신규 질문 A(경험 수준) |
|---|---|---|---|
| 묻는 것 | 사용자가 법적으로 누구인지 | 사용자가 무엇을 하려는지 | 사용자가 절차를 얼마나 아는지 |
| 위치 | Step1, 분석 전 | Step1, 분석 전 | Step2, 분석 직후 1회 |
| 영향 범위 | `getApplicableTasks()` 필터, 서류 그룹 매칭 | `getFitMessage()` 불일치 경고 | **표시 깊이·기본 펼침·용어 사전 강조만** |
| 판단 로직 변경 | 있음(어떤 task가 나오는지) | 있음(불일치 경고 발동 여부) | **없음** — task 추가/제거/필터링 금지 |

중복 없음, 역할 완전히 다릅니다. 두 기존 select는 "무엇을 보여줄지"를 결정하고, 신규 질문은 "어떻게 보여줄지"만 결정합니다.

## ⑷ 마찰 점검 결과

### P0

- doc-checklist 완료를 2단계 게이트로 쓰면 기존 카피와 직접 모순 → ⑴에서 반영 완료(게이트로 쓰지 않음).
- 잠긴 단계에서 원문 링크·질문 문구를 숨기면 상단 고지를 어김 → ⑴에서 반영 완료(정보 열람은 항상 열림).

### P1

- 순차 잠금은 "해본 적 있어요" 응답자에게도 매번 이전 단계를 체크해야 다음이 열리는 추가 클릭을 만든다. 질문 A의 효과를 표시 깊이로만 한정했기 때문에 잠금 자체는 우회하지 않는다.

- 온보딩 질문 A·B를 `report-hero` 바로 아래에 쌓으면 F자 스캔 패턴의 상단이 "말 거는 카드"로 채워진다. 질문 B는 새 카드를 만들지 말고 기존 `board-coach` 안의 질문 입력창을 끌어올리는 방식으로 카드 수를 늘리지 않는다.
- 현재 `board-status`는 "진행률" 카드 하나뿐이다. "지금 몇 단계인지"를 보여주는 요구사항은 정보구조만 명시하고 시각 형태는 visual-designer 판단으로 넘긴다.

### P2

`getAiPrecheckForTask`·`askAgency` 문구 생성 로직, 회차 파싱 수정분(`dc8a855`), doc-checklist "참고용" 카피, 상단 고지 밴드 문구, 금지 문구 14종(특히 "Q&A" 표기 금지).

## ⑸ visual-designer·frontend-implementer에게 넘길 때 주의할 점

- 변수명 `currentStage`/`pipelineSteps`는 이미 Step1 분석 파이프라인이 쓰고 있다. 새 단계 상태는 다른 이름(`prepStage` 등)을 쓴다.
- `getApplicableTasks()` 점수 정렬을 단계 경계 안으로만 한정한다. 그렇지 않으면 단계 그룹이 깨진다.
- `doc-checklist` 완료는 어떤 경우에도 2단계 게이트에 넣지 않는다.
- 잠긴 단계에서 체크박스만 비활성화하고, 링크·문의 문구·상세 설명은 항상 보이고 눌려야 한다.
- 화면 문구에 "Q&A"를 쓰지 않는다. "질문-답변"으로 쓴다. 구현 후 `tests/test_screen_strings.py` 재확인 필요.
- 질문 B는 새 카드를 만들지 말고 기존 `board-coach` 질문 입력창을 끌어올리는 방식으로, 상단에 카드가 쌓이지 않게 한다.
- 경험 수준 질문은 표시 로직에만 연결하고, `getApplicableTasks()`/`local_ai_coach()` 등 판단 로직에는 어떤 경로로도 연결하지 않는다.
- `nextTask` 재정의가 `currentNoticeCard().next`(관심 공고 탭)에도 영향을 주므로, 단계 재정의 작업과 같은 커밋에서 그 호출부도 함께 확인한다.
