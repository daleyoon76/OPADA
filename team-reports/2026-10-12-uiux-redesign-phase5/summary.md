# UX 전면 재설계 5단계(전체 phase 5/5, 마지막) — 전체 흐름 통합 검증 2026-10-14

솔로 작업(서브에이전트 병렬 호출 없이 직접 검토·수정·검증 수행). `agentic-journey` 브랜치, 워크트리 `Hometest_op-agentic`.

## 범위

새 기능을 추가하지 않고, phase1~4(마법사·1단계·2단계·3단계)를 처음부터 끝까지 한 번에 이어 검증하고 발견된 결함만 고쳤다.

## 1. 전체 흐름 통합 검증

전용 포트 19006에 직접 서버를 띄우고 실제 브라우저(OpenClaw browser 도구)로 1p(유형·목적) → 2p(URL) → 3p(분석 결과) → 전환화면 → 준비 보드 1단계 → 2단계 → 3단계까지 한 번에 눌러 확인했다. 실제 온비드 공고(`onbidPbancNo=887390`, phase2~4와 같은 샘플)를 분석했다.

- 1p→2p→3p→전환화면→준비 보드 전환이 모두 매끄러웠다. 3p에 "입찰 마감 지남" 배지가 정상 표시됐다(이 샘플은 phase2 때부터 만료 상태로 알려져 있다).
- 1단계: phase2의 만료 경고("입찰기간이 이미 지났습니다(2026-06-04 17:00 마감).")와 "처음으로 돌아가시겠어요?" 버튼이 정상 노출됐다. 체크박스 두 개를 체크하자 2단계로 자동 전환(진행률 2/4).
- 2단계: "공동입찰인가요?"/"대리입찰인가요?" 질문에 둘 다 "예"로 답하자 서류 그룹이 `["공통"]` → `["공동입찰", "대리입찰", "대리입찰 · 공동입찰", "공통", "대리입찰 추가 안내"]`로 바뀌는 것을 `document.querySelectorAll('.doc-group h4')`로 직접 확인했다 — phase3 리포트의 5개 그룹과 정확히 일치. 제출서류 체크박스 체크 후 3단계로 자동 전환(진행률 3/4).
- 3단계: "담당기관에 물어볼 질문 정리" 할 일이 사라진 것을 확인했다(phase4에서 제거한 그대로 유지됨). 입찰 참여 정보 리스트(입찰기간·입찰 장소·최저입찰가격)가 정상 표시됐다. AI 질문창(`#bid-ask-input`)에 "최저입찰가격은 얼마인가요?"를 입력해 실제로 호출했고, "공고 원문 기반 답변 / 최저입찰가격은 660,000원입니다."를 받았다 — 실제 모델 응답이다.
- 콘솔 오류는 `favicon.ico` 404(기존부터 있던 무관한 것) 외 0건.
- 모바일(390px)에서도 레이아웃이 깨지지 않았다(스크린샷으로 확인).

### 검증 중 겪은 실수(제품 버그 아님)

AI 질문창을 찾는 과정에서 `document.querySelectorAll('input[type=text], textarea')`로 아무 입력창에나 값을 넣고 `input` 이벤트를 발생시켰는데, 그 요소가 실제로는 2p의 URL 입력창(`#notice-url`)이었다. `#notice-url`에는 "입력 URL이 바뀌면 재분석이 필요하다"는 이벤트 리스너가 걸려 있어 분석 상태가 즉시 초기화됐다("아직 분석된 온비드 공고가 없습니다"). 샘플을 다시 불러와 재분석하는 것으로 복구했다 — 테스트 스크립트의 실수였고 제품 결함은 아니다. 이후에는 `#bid-ask-input`처럼 소스 코드에서 정확한 id를 확인한 뒤 조작했다.

## 2. "처음으로" 리셋 재확인

1단계 완료 후 "처음으로 돌아가시겠어요?" 버튼을 눌러 1p로 복귀하는 것을 확인했다(URL 입력칸이 비었고, `document.querySelector('.wizard-step.is-active, [id^="wizard-step-"].is-active')`의 id가 `wizard-step-profile`임을 확인). 이어서 "다음"→"샘플 불러오기"→분석을 다시 실행했고, 활성 단계가 `wizard-step-result`(3p)로 정상 전환되며 "목적과 입력 공고 유형이 맞습니다" 판정도 정상 출력됐다. phase1의 마법사 리셋과 phase2의 "처음으로" 분기가 phase3·4의 변경과 합쳐진 뒤에도 상태가 꼬이지 않는다.

## 3. 보관함 → 재방문 흐름 — 미구현 확인

phase3의 "내 보관함으로 보내기"는 `localStorage`의 `onbid-public-asset-doc-agent-locker-v1` 키에 공동입찰/대리입찰 답과 확정 서류 리스트를 실제로 저장한다(저장 직후 `localStorage.getItem(...)`으로 직접 확인). 하지만 **이 키를 읽는 코드는 저장 함수(`saveNoticeToLocker()`) 자신 말고는 레포 전체에 없다**(`grep -n "docLockerStorageKey" src/app.js` 결과 3줄 모두 저장 함수 안이다).

"관심 공고" 화면(`renderWatchlist()`)은 완전히 별개의 저장소(`즐겨찾기`·`최근 살펴본 공고`)만 읽어서 보여준다. 그 목록의 각 항목에는 "원문"이라는 외부 온비드 링크(`target="_blank"`)만 있을 뿐, 앱 내부에서 그 공고를 다시 불러와 2단계의 공동입찰/대리입찰 답을 복원하는 동작은 어디에도 없다.

**결론: 보관함 저장→재방문 복원은 미구현이다.** "내 보관함으로 보내기"는 쓰기 전용이고, 사용자가 그 데이터를 다시 볼 방법이 앱 안에 없다. 사용자 지시 범위("저장해서 나중에 다시 열어볼 수 있다")의 최소 요건 — 그 공고를 나중에 다시 찾을 수 있다 — 는 "관심 공고" 목록(별개 메커니즘)으로 느슨하게 충족되지만, 답변·서류 리스트의 실제 복원은 이뤄지지 않는다. 범위 밖 새 기능 추가이므로 이번에는 구현하지 않고 이 사실만 보고한다.

## 4. `aiTaskSignals`의 죽은 참조 정리

`src/app.js`의 `aiTaskSignals`(line 484 부근)에 남아 있던 `"agency"`·`"agency-question"` id 참조를 확인했다.

- `build_tasks()`(`src/server.py`)가 실제로 만드는 task id는 `notice-type`·`bid-period`·`price`·`documents` 4개뿐이다(코드로 직접 확인). `"agency"`·`"agency-question"`은 어떤 실제 task에도 매칭되지 않는 죽은 id였다.
- `taskIds: [..., "agency-question"]`(1번 그룹)에서 `"agency-question"`만 제거하고, `taskIds: ["agency", "agency-question"]`(4번 그룹)은 `taskIds: []`로 비웠다. 두 그룹의 `taskKeywords`/`checkKeywords`(키워드 기반 매칭)는 그대로 뒀다 — 이 부분은 실제 task의 제목·설명 텍스트와 키워드로 매칭되므로 죽은 코드가 아니다.
- **동작 변경 없음 확인**: `signal.taskIds.includes(task.id)`는 애초에 `"agency"`/`"agency-question"`이 배열에 있든 없든, 실제 task.id(`notice-type`/`bid-period`/`price`/`documents`)와 절대 일치하지 않으므로 항상 `false`였다. 제거해도 이 조건식의 결과는 모든 실제 입력에 대해 동일하다. `node --check src/app.js`로 문법 확인, 단위 테스트(275/275)·금지 문구 검사(20/20)·e2e(19/19)가 모두 그대로 통과하는 것으로 교차 확인했다.

## 5. e2e 테스트 인프라 정비

### 발견한 핵심 문제

`tests/screen.spec.js`의 `analyzeWith()` 헬퍼가 `await page.goto("http://127.0.0.1:8975/")`로 **포트를 절대 URL로 하드코딩**하고 있었다. `playwright.config.js`의 `use.baseURL`과 무관하게 항상 메인 워크트리(`Hometest_op`, 포트 8975)로 접속했다 — 그 결과 이 워크트리(포트 19005)에서 아무리 config를 바꿔도 테스트는 메인 워크트리의 원래(마법사 이전) 코드를 열어 `#profile-next`를 끝내 찾지 못하고 타임아웃났다. phase1~4가 "이 워크트리 전용 config가 없어 e2e를 못 돌렸다"고 남긴 기록의 실제 근본 원인이 바로 이것이었다 — config 부재는 증상이고, 하드코딩된 `page.goto()`가 원인이었다.

### 조치

1. **`playwright.config.worktree.js` 신설** — `OPADA_E2E_PORT`(기본 19005)로 이 워크트리 전용 포트를 쓴다. 메인 워크트리의 `playwright.config.js`(8975 고정)는 건드리지 않았다.
2. **`tests/screen.spec.js:162` 수정** — `page.goto("http://127.0.0.1:8975/")` → `page.goto("/")`로 바꿔 `use.baseURL`을 따라가게 했다. 메인 config의 baseURL도 8975이므로 메인 워크트리 쪽 동작은 그대로다(회귀 없음).
3. **통합 검증 중 처음으로 전체 실행되면서 드러난 기존 테스트 2건의 결함을 수정**(둘 다 phase3·phase1-이후 설계 변경과 테스트가 어긋난 것이지, 이번 phase5가 만든 결함이 아니다):
   - S1 테스트: phase3의 공동입찰/대리입찰 조건부 그룹 필터링(기본값 "아니오"→해당 그룹 숨김)을 반영하지 않고 "대리입찰신청서" 항목이 무조건 보인다고 가정하고 있었다. 체크리스트를 펼치고 "대리입찰 예"를 누르는 단계를 테스트에 추가했다.
   - "1단계를 모두 체크해야 2단계가 열리고 되돌리면 다시 잠긴다" 테스트: 2026-10-11 설계(커밋 전 "잠긴 단계는 기본으로 접는다" 변경, `src/app.js:2097-2099` 주석 참고)로 잠긴 단계가 `<details>`로 기본 접히게 됐는데, 테스트는 예전 "항상 펼쳐짐" 가정을 그대로 쓰고 있었다. 단계 헤딩(`<summary>`)을 먼저 눌러 펼치는 단계를 추가했다. **이 collapse 동작 자체는 의도된 설계이므로 제품 코드는 건드리지 않고 테스트만 현재 설계에 맞춰 고쳤다.**
4. **`EXPECTED_TEST_COUNT` 정정** — `tests/gate-reporter.js`의 이 상수가 16으로 고정돼 있었는데 실제 `test()` 수는 19개였다(이번 세션이 추가한 테스트는 없다 — 이전부터 쌓인 드리프트). 19로 정정했다.
5. **`workers: 1` 추가** — 기본 병렬 워커로 돌리면 헤드리스 크로미움 여러 개가 이 맥미니에서 자원을 다투며 매 실행마다 다른 테스트가 번갈아 타임아웃났다(N3 음성 → N4 음성 순으로 무작위 실패, 단독 실행 시엔 항상 통과 — 전형적인 자원 경합형 플레이키). 순차 실행으로 고정해 3연속 재현 테스트에서 모두 안정적으로 통과했다.

### 최종 결과

## 전체 재설계(phase1~5) 최종 요약

OPADA(Hometest_op)의 입력부터 입찰 참여까지 전체 사용자 여정을 4개 phase에 걸쳐 재설계했다 — ⑴ 입력~분석을 1p(유형/목적)·2p(URL)·3p(결과)·전환화면 4개 화면의 마법사로 분리(phase1), ⑵ 준비 보드 1단계에 입찰기간 만료·목적 불일치 경고와 "처음으로" 재시작 분기 추가(phase2), ⑶ 2단계에 공동입찰/대리입찰 조건부 질문과 서류 리스트 필터링, "내 보관함으로 보내기" 저장 추가(phase3), ⑷ 3단계에서 "담당기관에 물어볼 질문 정리"를 제거하고 입찰 참여 정보 리스트·AI 질문창으로 대체(phase4). 이번 phase5는 새 기능 없이 네 phase를 처음부터 끝까지 실제 브라우저로 한 번에 이어 검증했고, 그 과정에서 e2e 테스트 스위트가 애초에 이 워크트리에서 한 번도 제대로 실행된 적이 없었다는 것(포트 하드코딩이 근본 원인)과 보관함 저장이 쓰기 전용이라 복원되지 않는다는 것, 두 가지 실질적인 공백을 찾아 전자는 고치고 후자는 범위를 지켜 보고만 남겼다. 전체 흐름(1p부터 3단계 AI 질문창까지)과 "처음으로" 리셋 후 재진행은 상태 꼬임 없이 매끄럽게 동작하는 것을 실제 브라우저로 확인했다.
