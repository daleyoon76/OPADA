# AI 코치 패널 다듬기 + /api/ask 속도 제한 (2026-10-14)

UX 전면 재설계(phase1~5) 위에 올리는 작은 체크포인트. 완전히 새로운 챗봇을 만들지 않고, 기존
"AI 코치에게 물어보기" 전역 패널과 준비 보드 3단계(입찰참여) AI 질문창을 그대로 다듬었다.

## 변경 범위

1. **`src/server.py` — `/api/ask` 속도 제한 신설**
   - 분석 전 코드를 직접 읽어 확인한 결과, 기존 `/api/ask` 핸들러에는 호출 횟수 제한이
     전혀 없었다(`[관측]`).
   - 로그인이 없는 서비스라 `self.client_address[0]`(요청자 IP)를 식별자로 쓰는
     메모리 내 카운터를 추가했다. 서버 재시작 시 리셋되며, DB는 범위 밖이라 쓰지 않았다.
   - 한도: **IP당 분당 5회 · 시간당 30회**. 슬라이딩 윈도(`deque` + `threading.Lock`)로
     스레드 세이프하게 세고, 초과 시 `429`와 `{"ok": false, "error": "질문이 너무 많습니다. …"}`
     를 반환한다.
   - 프런트엔드(`askNoticeQuestion`·`askBidParticipationQuestion`)는 이미
     `payload.ok`가 거짓이면 `payload.error`를 결과 영역에 그대로 보여주는 공용 처리
     경로를 쓰고 있어서, 화면 쪽 코드는 따로 고치지 않고도 안내 문구가 자연스럽게 뜬다.

2. **`src/styles.css` — `.coach-ask-card` 다듬기**
   - 실제로 띄워 확인한 결과(아래 스크린샷), 패널 자체가 숨겨져 있거나 접힌 상태는
     아니었지만, 다른 카드들과 똑같이 얇은 테두리 + 그림자 없는 배경이라 페이지의
     다른 정보 카드들 사이에 묻혀 눈에 덜 띄었다(`[관측]`).
   - 레이아웃 위치나 구조는 바꾸지 않고, 기존 `.fit-panel`·`.panel` 이 이미 쓰던 관용
     표현(왼쪽 강조선 `border-left` + `box-shadow: var(--shadow)`)을 그대로 가져와
     입혔다. 제목 글자 크기도 15px → 16px로 살짝 키웠다.
   - 이 클래스는 전역 패널(`renderBoardCoach`)과 3단계 AI 질문창(`renderBidAskBox`)이
     공유하므로, 두 곳 모두 같은 다듬기가 적용된다.

## 패널 다듬기 전후 비교

- 전: 얇은 1px 테두리만 있고 그림자가 없어 주변 카드와 시각적 구분이 약했다.
- 후: 왼쪽에 4px 주황 강조선(`var(--green)`, 브랜드 포인트 컬러)과 `box-shadow`가 더해져
  스크롤 중에도 "할 일"·"공고 요약" 같은 다른 카드보다 한 단 떠 보인다.
- 브라우저로 직접 띄워 스크린샷으로 대조했다(아래 "검증 내역" 참고). 전체 레이아웃·배치는
  그대로 두었다.

## 같은 속도 제한 공유 확인

- 전역 패널(`askNoticeQuestion`)과 3단계 질문창(`askBidParticipationQuestion`) 모두
  `window.fetch("/api/ask", …)`를 그대로 호출한다. 서버 쪽 속도 제한은 요청 바디가 아니라
  경로(`/api/ask`)와 호출자 IP만 보고 걸리므로, 코드 읽기로 두 창이 같은 카운터를 공유함을
  확인했다(`[관측]` — 코드 경로 대조. 3단계 화면 자체는 2단계를 다 마쳐야 열리는 잠금
  상태라 이번 검증에서는 UI로 직접 열어보지 않았다).

## 검증 내역

- **단위 테스트**: `python3 -I tests/test_docs_extraction.py` → **275/275 통과**
- **금지 문구 검사**: `python3 -I tests/test_screen_strings.py` → **20/20 통과**
- **e2e**: `npx playwright test --config=playwright.config.worktree.js` → **20 passed**
  (게이트 리포터 자체 집계는 "19/19"로 표시하나, playwright 실행 결과는 20개 테스트
  전부 통과·실패 0건. 변경 전후 테스트 목록·개수에 변동 없음)
- **속도 제한 동작 확인(curl, 전용 임시 포트 19100)**:
  같은 IP로 `/api/ask`에 7회 연속 요청 → 1~5번째 `200`, 6~7번째 `429`
  (`{"ok": false, "error": "질문이 너무 많습니다. 1분 후 다시 시도하세요."}`)
- **속도 제한 동작 확인(실제 UI, 같은 임시 포트)**:
  준비 보드의 "AI 코치에게 물어보기" 질문창에서 "질문하기"를 6회 연속 클릭 →
  서버 로그(`POST /api/ask`) 대조 결과 **200이 5회, 429가 1회** — 정상 한도(분당 5회)와
  일치. 정상 범위 내 질문(1~5번째)은 실제 LLM 연결 답변("공고 원문 기반 답변" 배지)이
  화면에 그대로 떴다 — 제한이 정상 사용 경로를 막지 않음을 함께 확인했다.
- 두 임시 테스트 서버(포트 19100)는 검증 후 종료했고, `git status --short`로 임시 산출물이
  남지 않았음을 확인했다.
