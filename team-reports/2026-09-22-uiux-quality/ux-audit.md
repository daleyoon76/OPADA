## 작은 개선 제안

### 결정 A — board-status 카드 제거, 구체 위치와 방식

- 대상: `app.js:1476-1491`의 `board-status` 배열에서 `["AI 우선 액션"/"다음 액션", ...]` 항목 삭제. `["진행률", ...]` 항목만 남긴다.
- 레이아웃 위험: `board-status`는 현재 2단 그리드다(`grid-template-columns: minmax(260px, 1.6fr) minmax(200px, 0.9fr)`, `styles.css:736`). 카드 1개만 남기면 좁은 칼럼(0.9fr) 카드 하나가 혼자 남아 균형이 깨진다. 두 가지 안 중 택 1.
  - 안 1(최소 변경): `board-status` 섹션 자체를 없애고, "진행률" 막대를 `task-panel`의 `panel-heading`(`index.html:100-107`, "초기화" 버튼 옆)으로 옮긴다. "얼마나 했는지"는 태스크 목록 헤더에 붙는 것이 자연스럽고, "무엇부터 할지"는 이미 정렬된 `task-list` 1번 항목이 대신한다.
  - 안 2(레이아웃 안 건드림): `board-status` 컨테이너는 유지하되 `grid-template-columns: 1fr`로 바꿔 진행률 카드 하나가 전체 폭을 쓰게 한다. 변경 범위가 CSS 한 줄 + JS 배열 한 줄로 가장 작다.
  - 팀장 판단: 화면 상단 공간을 아끼려면 안 1, 구현 리스크를 최소화하려면 안 2.

### 결정 B — "AI가 짚은 빈칸" → 대안 문구

- 위치: `app.js:1522`, `task-item`의 `<details><summary>담당기관에 물어볼 문장</summary>` 안, `aiMatch.check.reason` 앞 라벨.
- `reason` 텍스트 실제 내용(`server.py:1364,1383,1392,1405,1411,1417` 등)은 전부 "~이유/~때문에" 설명형 문장이다. 예시안 "확인이 필요한 이유"가 내용과 맞다.
- 같은 `reason` 데이터가 `renderCoachPanel`의 board 모드(`app.js:951-955`)에서는 라벨 없이 `<p>{reason}</p>`로 그대로 노출된다. 문구를 바꿀 때 이 두 위치(task-item details / coach-check article)를 같이 보되, 최소한 coach-check 쪽에도 같은 라벨(`<b>확인이 필요한 이유</b>`)을 붙여야 같은 개념이 두 가지 표현으로 흩어지지 않는다.

### 결정 C — 입찰기간/최저입찰가격 통일 문구 + 원문 링크

- 현재 구조 확인: `task-item`(`app.js:1499-1511`)은 이미 title(라벨)+action(`<em>` 값)+due(배지)+"온비드 원문" 링크(`task-meta`, 1510)를 전부 갖고 있다. 원문 링크 자체는 이미 항상 렌더된다 — 없는 것은 "링크"가 아니라 "값 없음과 값 있음을 다르게 보여주는 분기"다.
- 제안 순서:
  1. 서버 쪽 fallback 문자열 5곳(`server.py:1255-1256`(bid-period task), `1235`(price task), `1311-1312`(local_ai_coach facts), `2244`(alerts), `app.js:914-915`(preview-grid, 분석 결과 화면))을 공용 문자열 하나로 합친다. 이건 화면 문구 정리의 전제이며, 하나만 바꾸면 나머지 4곳이 옛 문구로 남아 화면마다 다시 갈라진다.
  2. `task-item`의 `<em>` 값 자리를 값 유무로 분기: 값이 있으면 지금처럼 그대로, 값이 없으면 "자동으로 찾지 못했습니다" 같은 정직한 실패 문구 + 바로 옆에 "원문에서 확인하세요" 안내. 지금은 원문 링크가 `due` 배지 옆(1508-1511)에 있어 실패 문구와 시선이 분리돼 있다 — 실패 문구 바로 곁에 링크(또는 링크 텍스트)를 재배치하는 것을 함께 검토.
  3. 이 값은 `coach-facts`(943-948)에도 같은 필드로 다시 나타나므로, 문구 하나를 바꾸면 화면 두 곳(task-item, coach-facts) + 분석 전 미리보기(preview-grid) + 상단 alerts까지 총 4개 렌더 지점을 함께 확인해야 한다.
- 회차 파싱 자체(`known-pitfalls.md:46`, `to-do.md:113`, `failure-mode-round-parsing.md` §2)는 이번 범위 밖이라 구현해도 여전히 빈 값이 뜬다. 결정 C의 성공 기준은 "빈 값이 0"이 아니라 "빈 값일 때 문구가 일관되고 정직한가"로 잡아야 한다.

### 결정 D — 실패 문구 시각적 구분

- `architecture-audit.md` §3이 이미 `confirmedFacts` 항목에 `status: "extracted" | "fallback"` 필드 추가를 제안했다. UX 관점에서 그 상태를 어떤 시각 언어로 표현할지 제안한다.
  - "extracted": 지금의 amber 톤 유지. 이미 사용자가 "원문에서 읽은 값"으로 학습한 색이라 바꿀 이유가 없다.
  - "fallback": 값 자리 옆에 배지를 병기한다. `docChecklistStatusBadge`(`app.js:1102-1109`, "추출됨"/"본문 미기재"/"원문에 없음"/"추출 실패")가 이미 서류 체크리스트에서 쓰는 용어·색을 그대로 재사용하면, 사용자가 이미 본 색·용어를 여기서 다시 보게 되어 새 학습 비용이 없다. 예: fact.value 텍스트 뒤에 `badge("추출 실패", "warn")`을 작게 병기.
- 팔레트 제약: 이번 개선은 `--muted`/`--soft-neutral`/`--amber`/`--soft-amber`/`.badge.warn`/`.badge.neutral`(전부 기존 정의, `styles.css:1189-1204`) 재사용만으로 충분하다고 판단한다. 새 CSS 변수·새 색상 추가는 "테마 변경 금지" 요건 위반 소지로 본다(아래 위험 항목 참고).

## 조사 2 — 라벨/값 위계·static/variable 색 구분이 적용돼야 할 화면 구역 전체

- `preview-grid`(`app.js:911-916`, "공고 분석" 결과 미리보기, `view-input`의 `analysis-result` 패널 안) — `styles.css:356-380`.
- `coach-facts`(`app.js:946-948`, "AI가 탐지한 내용", `board-coach` 안) — `styles.css:440-474`.

- `quick-facts`/`fact-row`("공고 요약" 패널, `app.js:1540-1559`) — `styles.css:958-971`.
- 서류 체크리스트 항목(`renderDocChecklist` 부근, `docSourceBadge`/`docChecklistStatusBadge` 사용) — 라벨/값 쌍이 아니라 "서류명 + 상태 배지" 조합이라 패턴은 다르지만, static(위치 안내: "본문에서 찾을 수 있음")과 variable(서류명)이 이미 배지/텍스트로 분리돼 있어 오히려 참고 선례로 제안한다.
- `task-item`(`app.js:1499-1511`) — title(정적 라벨)과 action(변수 값)이 각각 `<strong>`/`<em>` 태그로 이미 구분되나, 해당 CSS(`styles.css:813-945` 대역)의 실제 굵기·색 차이는 이번 조사에서 끝까지 대조하지 않았다. 미확인으로 남긴다.
- `coach-check` 문장 내부(서버가 만드는 `reason` 문자열, 백틱 인용된 값 포함, 예 `server.py:1364`) — 태그 레벨이 아니라 순수 텍스트 안에 섞여 있어 지금 구조로는 색 구분이 불가능하다. 구현하려면 서버가 값 부분을 별도 필드로 분리하고 클라이언트가 감싸는 태그를 새로 만들어야 한다 — 이번 조사에서 새로 발견한 항목.
- `report-hero` 상단 한 줄(`app.js:1458`) — 라벨 자체가 없다. "라벨/값 구분이 약하다"가 아니라 "라벨이 없다"는 별도 결함이며, 같은 데이터를 `preview-grid`에서는 라벨과 함께 보여주는 것과 대조된다.

## 조사 3 — "확인 필요 항목"이 사용자 입력을 무시하는 것처럼 보이는 문제, 문구 수준 완화안

- 근본 원인(서버가 `user-type`/`asset-focus`를 아예 안 받음)은 `architecture-audit.md` §1에 있고, 이번 범위 밖이다. 아래는 코드 변경 없이 문구만으로 오해를 줄이는 안이다.
- 사실 확인: `getApplicableTasks()`(`app.js:746-755`)와 `DOC_GROUP_CONDITION_USER_TYPES`(`app.js:1128` 부근)는 `user-type`으로 태스크·서류 그룹을 실제로 필터링한다. 즉 "완전히 무시"는 사실이 아니고 "서류 조건 필터링에는 반영되지만, 코치 문구·업종 적합성 판정에는 반영되지 않는다"가 정확하다.
- 완화안 1: `task-panel` 헤더(`index.html:100-107`)나 `coach-head`(`app.js:960-971`) 근처에 "이 체크리스트는 온비드 원문 기준이며, 위에서 고른 사용자 유형은 서류 조건 필터링에 반영됩니다"류의 스코프 고지 문장을 추가한다. `asset-focus`(업종 적합성)까지 반영된다고 암시하는 문구는 넣지 않는다 — `architecture-audit.md` §2가 그 판정은 지금 데이터로 불가능하다고 명시했다.
- 완화안 2: `local_ai_coach`의 "확인 필요 항목"(예: "내 업종으로 실제 사용 가능한지", `server.py:1404`)은 `asset-focus` 입력과 무관하게 `is_sale` 두 분기로만 고정 노출된다. 이 항목들 제목 옆에 "이 유형(임대/대부) 공고 공통 확인 항목" 같은 정적 태그를 붙이면, "내 입력이 무시됐다"는 인상 대신 "이건 애초에 개인화가 아니라 공통 체크리스트"라는 프레이밍으로 바뀐다. 정직하고 구현 비용이 낮다.
- 실제 대조 로직 신설(진짜 업종-용도 매칭)은 범위 밖이며 `to-do.md`에 이미 근접 항목(`architecture-audit.md` "제품 판단이 필요한 지점")이 있으니 중복 등재하지 않는다.

## 보존 자산/요건 해석 위험

- 결정 A 구현 시 `board-status`의 2단 그리드(`styles.css:736`)가 카드 1개로 어색해질 위험 — CSS를 함께 조정하지 않으면 구현 후 화면이 비어 보이거나 불균형해진다.
- 결정 C의 "문구 통일"은 서버 3곳 + 클라이언트 2곳, 총 5개 렌더 지점(위 결정 C 목록)에 흩어진 fallback 문자열을 모두 찾아 바꿔야 완결된다. 하나만 고치고 완료로 보고하면 화면 나머지 3~4곳은 옛 문구로 남는다.
- 팔레트/폰트 변경 금지 제약 — 결정 D 구현 시 "실패"를 나타낼 새 색상 변수를 만들고 싶은 유혹이 있을 수 있다. 기존 `--muted`/`--soft-neutral`/`.badge.warn`/`.badge.neutral` 재사용으로 충분하다고 판단하며, 새 CSS 변수 추가는 테마 불변 요건 위반 소지로 P0 위험으로 표시한다.
- `coach-check`의 `reason` 문자열에 서버가 백틱(`` ` ``)으로 감싼 인용 표기가 이미 있다(`server.py:1364`). `app.js`가 마크다운 파서를 쓰는지 확인하지 않았다 — 백틱 문자가 그대로 화면에 노출되는지, 별도 스타일로 변환되는지 **미확인**이다. static/variable 색 구분을 문장 내부까지 확장하기 전에 이 기존 표기가 실제로 어떻게 보이는지부터 스크린샷으로 확인해야 새 강조와 충돌하지 않는다.
- `known-pitfalls.md:46`/`to-do.md:113`(회차 공고 입찰기간 파싱 실패)은 이번 조사가 그대로 승계한다. 결정 C는 "문구만 정리"이지 "파싱을 고친다"가 아니라는 점을 구현 담당자에게 다시 명시한다 — 통일된 새 문구를 적용해도 회차 공고(표본 23/23 실패, `failure-mode-round-parsing.md` §2)는 여전히 빈 값이다.

## 검증할 사용자 행동

- `board-status` 카드 제거 후, 사용자가 `task-list` 최상단 항목만 보고 "다음에 뭘 해야 하는지"를 곧바로 알아채는지 — `getApplicableTasks()`의 정렬(aiMatch score 기준, `app.js:752-755`)이 실제로 우선순위 항목을 맨 위로 올리는지 라이브 화면에서 재확인.
- "확인이 필요한 이유"(또는 최종 채택 문구)로 바꾼 뒤, `task-item`의 `details`를 열어본 사용자가 그 문구를 "왜 체크해야 하는지 이유"로 자연스럽게 읽는지.
- 입찰기간 값이 있는 정상 공고(hidden input 성공 케이스)와 없는 공고(회차 공고, 23/23 실패 케이스) 둘 다 열어, 통일 문구 적용 후에도 "값 있음/없음"이 첫눈에 구분되는지.
- `coach-facts`에 fallback 배지를 붙인 뒤, 사용자가 배지 텍스트만으로 "이건 실패한 추출"이라는 것을 읽는지(팔레트 고정 제약상 색 대비 개선은 이번 범위 밖).
- `task-panel` 헤더에 스코프 고지 문장을 추가한 뒤, 사용자가 "내가 고른 사업자 유형이 완전히 무시됐다"는 오해를 덜 하는지 — 가능하면 실제 사용자 발화를 다시 수집해 대조.
