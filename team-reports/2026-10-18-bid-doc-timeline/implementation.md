## 2. 선행 검토 지적을 어떻게 처리했는가

### P0-1 · 빈 단계가 「완료」로 표시되는 것 — 처리했습니다

`getPrepStageStatus()` 에 네 번째 상태 `notYet` 을 더했습니다. 판정 순서는 설계가 지정한 대로 `locked → notYet → done → active` 입니다.

두 겹으로 막았습니다.

- 파생값에서 막습니다. `done: notYet ? false : done` 으로 눌러, 반환 객체 자체가 「완료」를 주장하지 못합니다. `[].every()` 가 참이라는 성질이 4단계에 닿지 않습니다.
- 표시에서도 막습니다. `renderPrepStageStepper()` 와 `renderStageHeading()` 둘 다 `notYet` 을 `done` 보다 먼저 봅니다. 한쪽만 고치면 스테퍼와 목록 헤딩이 어긋나므로 두 함수를 같이 고쳤습니다.

`notYet` 은 `sequential: false` 인 단계에만 붙습니다. 4단계는 항목이 있어도, 사용자가 미리 체크해 두어도 `notYet` 입니다. 이 서비스는 낙찰 여부를 알 수 없고, 알 수 없는 것을 「도달했다」로 추정하지 않기 때문입니다. `sequential` 인 단계가 공집합일 때의 기존 동작(공집합 완료로 보고 다음 단계를 막지 않음)은 그대로 뒀습니다. 테스트 픽스처가 `documents` 하나만 주는 경우를 그 동작이 지탱하고 있어서입니다.

보드 렌더의 조기 반환(`if (!stageTasks.length) return ""`)도 함께 고쳤습니다. 이것을 두면 4단계가 스테퍼에만 남고 목록에서는 사라져, 「목록에는 없는 단계」가 됩니다. P0-1의 나머지 절반입니다.

- **실제 공고 데이터로 돌려 보지 않았습니다.** 브라우저 확인과 e2e는 모두 `tests/screen.spec.js` 의 `stagedNotice()` 픽스처로, `fetch` 를 가로채 쓴 것입니다. 실제 온비드 공고를 분석했을 때 `CONTRACT_STAGE_RE` 가 서류를 어떻게 나누는지는 재지 않았습니다.
- 🔴 **`CONTRACT_STAGE_RE` 의 단계 판정 정확도를 재지 않았습니다.** 선행 검토의 researcher-fact-check §4가 「다음 작업의 1순위」로 적은 항목이고, 이번 범위 밖이었습니다. 지금 구조는 그 판정이 틀려도 비싼 쪽 오류를 피하도록 설계돼 있지만(비대칭 기본값 + 머리 안내), 「얼마나 틀리는가」는 모르는 상태입니다.
- **낙찰 후 일반 안내 8항목의 내용은 공고 원문 대조를 하지 않았습니다.** 설계가 지정한 문구를 그대로 옮겼고, 그 설계가 근거로 삼은 것은 선행 검토의 압류재산 공고문 인용입니다. 묶음 2의 소유권이전 서류 6건은 설계 문서가 제시한 목록이며, 제출처는 확인되지 않아 단정하지 않았습니다.
- **재산유형별 차이를 확인하지 않았습니다.** 낙찰 후 안내는 재산유형과 무관하게 모든 공고에 붙습니다. 묶음 1은 「(압류재산)」이라고 제목에 적었지만, 국유재산·공유재산 공고에서도 그 묶음이 보입니다. 설계가 「재산유형과 무관하게 일반 안내로 넣되」라고 지시한 대로입니다.
- **다른 화면 폭에서 보지 않았습니다.** 1280×1600 하나로만 확인했습니다. 4단계 블록과 파선 테두리가 모바일 폭에서 어떻게 보이는지는 모릅니다.
- **배포하지 않았습니다.** 푸시도 하지 않았습니다.
- **`buildLockerRecord()` 의 변화를 따로 재지 않았습니다.** 이 함수는 `getVisibleDocGroups()` 를 쓰므로 「내 보관함으로 보내기」의 서류 목록에 낙찰 후 8항목이 함께 들어갑니다. 기존 테스트가 통과했고 설계가 이 범위를 지정하지 않아 그대로 뒀습니다.

## 5. 다음 작업

1. **`CONTRACT_STAGE_RE` 정확도 측정.** 표본 23건에 정규식을 돌려 「입찰 전인데 낙찰 후로 분류된」 건수를 셉니다. 이번 설계는 그 오류를 비싸게 만드는 변경이므로, 비대칭 기본값과 머리 안내가 충분한 안전망인지 이 수치로 판정해야 합니다. 선행 검토가 1순위로 꼽은 항목입니다.
2. **입찰참가신청 필요 여부 추출 경로.** 온비드 공고 상세의 「입찰참가신청」 항목을 뽑는 경로를 서버에 더합니다. 같은 HTML 안에 PC·모바일 두 벌의 변형 문구가 있다는 것이 선행 조사에서 확인됐으므로, 문자열로 찾는 코드는 두 문구를 모두 고려해야 합니다. 값이 생기면 그때 2단계 맨 위에 둘지 다시 판단합니다.
3. **공공데이터 API `getCltrBidInf2` 연동 검토.** 15개 제출서류 필드의 실제 값을 먼저 봐야 합니다. 이 기기에 `ONBID_API_SERVICE_KEY` 가 없어 41일째 미확인 상태입니다. 키를 받는 것이 선행 조건입니다.
4. **운영 배포.** 이번 변경은 `-agentic` 작업 트리에만 있습니다. 운영 경로 반영은 별도 판단이 필요합니다.
5. **e2e 설정의 포트 점유 문제.** `reuseExistingServer: true` 와 고정 포트 8975의 조합 때문에, 운영 서버가 떠 있으면 작업 트리의 e2e가 조용히 운영 코드를 검사합니다. 실패가 아니라 «통과»로 끝나기 때문에 알아채기 어렵습니다. 포트를 워크트리마다 다르게 두거나, 서버가 어느 경로를 서비스하는지 확인하는 단정을 한 줄 넣는 것을 권고합니다.
6. **낙찰 후 안내의 재산유형 분기.** 묶음 1은 압류재산 공고문에 근거한 것인데 지금은 모든 재산유형에 보입니다. 제목에 「(압류재산)」을 적어 두었지만, 재산유형을 읽어 해당하지 않는 묶음을 접거나 숨기는 것이 나은지 판단이 필요합니다. 이번에는 설계 지시대로 전부 노출했습니다.
