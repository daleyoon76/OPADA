## 2. 제품 동작이 틀린 것으로 판정한 항목과 근거 조문

**결함**: `DOC_CONDITION_SUPPLEMENT.joint`(`src/app.js`)의 "공동입찰참가신청서" 항목에 붙는 note가 재산유형을 가리지 않는 전역 상수였다. 공동입찰 질문에 "예"로 답하면 재산유형과 무관하게 "압류재산 공매는 인터넷 공매이므로, 공동입찰신청을 온비드 등록으로 대신할 수 있습니다"가 그대로 떴다. [관측 · 시나리오 3 음성 대조 테스트 1회차 실패로 발견]

**판정 근거(설계서 §1 갈래 ⑶, 둘 다 researcher-fact-check.md에서 직접 재확인)**:
- 압류재산 공매공고문 「16. 주의사항」 자항 ③호 단서: "다만, 인터넷 공매의 경우에는 공동입찰신청을 온비드 등록으로 대신할 수 있습니다"(사실 1 [인용] — HTTP 200 원문 직접 대조).
- 국유재산 대부입찰 공고문 「2. 입찰참가자격」: 이 단서가 없고 "공동입찰의 경우 전자서명 방식 또는 서류제출 방식 중 선택할 수 있으며"를 대신 제시한다(사실 3 [인용] — HTTP 200 원문 직접 대조).

두 공고문이 서로 다른 절차를 규정하므로, 하나의 note를 재산유형 구분 없이 재사용하는 것은 국유재산 사용자에게 실제로 없는 절차를 안내하는 결함이다.

**수정 범위**: `buildDocConditionSupplementItem()`에 `noteAssetTypes` 조건을 추가해, 서류 항목 자체(공동입찰참가신청서)는 재산유형과 무관하게 그대로 띄우되 압류재산 전용 note만 압류재산 공고에서만 붙게 했다. 국유재산 전용 대체 문구("전자서명 방식 중 선택")는 **추가하지 않았다** — 설계서 §3 시나리오3의 음성 대조는 "압류재산 전용 문구가 안 뜨면 된다"까지만 요구했고, 국유재산 전용 안내를 새로 만드는 것은 이 설계서의 범위 밖이다.

## 3. 통과해야 하는 입력이 실제로 짝으로 들어갔는지

- **시나리오 1**: 기본 상태(미답변)에서 0건 단정 + 대리입찰 "예" 클릭 시 뜸(음성 대조) 모두 포함. 실행 확인됨.
- **시나리오 2**: "또는 본인서명사실확인서" 표기 단정 포함. 음성 대조는 설계서 원문("공동입찰·미성년자 조건 서류는 안 뜸")에서 **미성년자를 뺐다** — 아래 §3-2에서 이유를 적는다.
- **시나리오 3**: 국유재산 음성 대조 포함, 1회차 실패 → 결함 발견 → 수정 → 2회차 통과.
- **시나리오 5**: "사전에 있는 표제(대리입찰신청서)는 미분류 구획에 안 들어간다" 음성 대조 포함.
- **시나리오 4·6**: 기존 S10·P0-1 테스트의 음성 대조(재산유형 불명 시 펼침 유지, 체크 전부 해도 4단계는 미완)가 그대로 살아 있고, 이번 실행에서도 통과했다.

### 3-1. 시나리오 2 음성 대조를 조정한 이유

설계서 원문은 "공동입찰·미성년자 조건 서류는 대리입찰만 예를 누른 화면에 뜨지 않아야 한다"고 적었다. 그런데 "미성년자" 조건은 `getVisibleDocGroups()`의 필터 대상이 아니다 — 코드는 `label.includes("공동입찰")`·`label.includes("대리입찰")`만 사용자 답변에 연동시키고, "미성년자"는 답변 질문 자체가 없는 상시 노출 조건이다. 기존 S2 테스트(`screen.spec.js:177~`)도 이미 "대리입찰 예" 클릭 뒤 "미성년자"가 보임을 전제로 단정하고 있다. 이 부분은 설계서가 미성년자 조건의 실제 구조(질문 UI 없음)를 반영하지 못한 서술로 판단해, 시나리오 2의 음성 대조를 "공동입찰 서류는 안 뜬다"로 좁혔다. §1 정답 출처 표에도 미성년자 조건이 proxy 답변에 연동돼야 한다는 조문 근거가 없다. [추론 · 기존 S2와의 충돌 관측에 근거, 제품을 고치지 않고 테스트 서술만 조정함]

## 4. 설계서가 미확인으로 남긴 두 가지의 확인 결과

### 4-1. 시나리오 1·3이 실제로 화면에 그렇게 뜨는가

실제로 실행해 확인했다.
- 시나리오 1: 실행 1회차부터 통과 — 코드 읽기로 추정한 게이트 동작과 실제 화면이 일치했다.
- 시나리오 3: 실행 1회차에서 **음성 대조가 실패**했다 — 코드 읽기만으로는 보이지 않던 결함(§2)이 실제 실행에서 드러났다. 이것이 바로 설계서가 "실제로 실행해야만 확정된다"고 적은 이유를 실증한 사례다.

### 4-2. `public-data-status.spec.js`가 실제로 실패하는지, 원인이 네트워크 의존인지

실제로 실패하는 것을 확인했다. 원인은 **네트워크 의존이 아니었다** — `#asset-focus`(목적 선택, 마법사 1단계)를 `#profile-next` 클릭(2단계로 전환) **뒤에** 선택하려 해서 요소가 안 보여 30초 타임아웃이 났다. 2026-10-12 입력 마법사를 1단계(목적)/2단계(URL)로 분리하면서 이 테스트의 선택 순서가 낡은 것이었다. 순서를 "asset-focus 선택 → profile-next 클릭"으로 바꾸자 9.4초 안에 통과했고, 실제 온비드 API 호출(`/api/analyze?url=...`)도 200으로 성공했다 — 즉 온비드 네트워크 자체는 이 세션 동안 정상이었다.

## 6. global-setup 거부 장치 실제 작동 확인

작업 착수 전 `src/app.js` 끝에 임시 주석 한 줄을 추가하고 `OPADA_PORT=8975`(운영 서버, PID 78800)로 돌려 global-setup이 바이트 불일치를 실제로 거부하는지 확인했다. 거부 메시지(`🔴 … 서버가 이 작업 트리의 코드를 서비스하지 않습니다`)가 떴고, 즉시 그 줄을 제거해 `git status --short` 공백을 확인했다. 그 뒤 모든 실행은 빈 포트 19201을 썼다. [관측 · 실행 재현]

참고로 조사 중 포트 8975(운영 레포 `Hometest_op`)와 이 작업 트리의 `src/app.js`가 바이트까지 동일한 상태였다(`diff` 0줄) — 두 레포가 같은 코드 상태라 거부 장치의 "같으면 통과" 분기가 자연스럽게 걸렸고, 그래서 위 임시 변경으로 "다르면 거부"하는 쪽을 따로 재현했다.

## 8. 못 한 것과 그 이유

- **국유재산 전용 공동입찰 안내 문구 추가**: 설계서 §3 시나리오3의 음성 대조가 요구한 범위(압류재산 전용 문구가 안 뜨면 됨)를 넘는 작업이라 하지 않았다. 필요하면 별도 작업으로 설계해야 한다.
- **`public-data-status.spec.js`를 "온비드가 죽었을 때 건너뛰기(skip)"로 바꾸는 것**: 설계서 §4가 "권고로만 적고 실행하지 않는다"고 명시했고, 이번 작업 지시도 그 변경을 요구하지 않았다. 셀렉터 순서만 고쳤고 skip 전환은 하지 않았다.
- **`.deploy-backups/`(git status 미추적) 조사**: 설계서 §5-3이 이미 이번 설계 범위 밖으로 선언했고, 이번 작업도 건드리지 않았다.
